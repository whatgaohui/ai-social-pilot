# 项目改善方案 — 从混乱到规范

> 基于对项目现状的深入分析，制定可执行的改善方案。
> 制定日期: 2026-05-07

---

## 一、问题诊断

### 1.1 Git 执行缺失

**表现**: 项目核心代码（账号中心重构、内容库、巡检系统等约 220KB、12 个文件）从未提交到 git，只有后续 E2E 测试报告和文档更新有提交记录。

**根因**: 每次迭代完成后直接进入下一个需求，跳过了 git 提交步骤。工作日志写得太详细，产生了"已经记录了 = 已经完成"的错觉。

**数据**: 23 个 git 提交中，9 个是 E2E 报告数字更新，3 个是单独更新 worklog，只有 10 个是真正的代码改动。而最核心的代码（Iteration 004-008）全部未提交。

### 1.2 工作区结构缺失

**表现**: 项目根目录混杂了代码文件、文档、脚本、数据库、测试报告，没有分区管理。

| 缺失目录 | 作用 | 现状 |
|----------|------|------|
| `assets/bug/` | Bug 截图归档 | E2E 截图散落在 `test-results/`，无 bug 截图 |
| `assets/reference/` | 参考设计、竞品截图 | 无 |
| `notes/` | 技术知识沉淀 | 无。踩过的坑没有记录 |
| `AGENTS.md` | AI 入职说明书 | 无。每次新对话都要重新交代 |

### 1.3 开发流程跳过关键步骤

| 步骤 | 应该做 | 实际做 |
|------|--------|--------|
| 讨论+文档化 | 先把想法变成 PRD | 用户一句话直接开发 |
| 先做 Demo | 最小成本先看到效果 | 直接开发完整功能 |
| 补全逻辑+计划 | AI 补全分支流程、制定开发计划 | 有时有计划，有时没有 |
| 开发+测试+学习 | 遇到坑记笔记 | E2E 报告只记"通过了"，不记学到了什么 |

### 1.4 知识资产为零

文章强调"每一个踩过的坑都记录下来，解决一个问题，沉淀一份知识"。

我们有 `docs/e2e-iteration-report.md`，但内容全是"9/9 通过 ✅，无新增问题"，没有任何问题分析、技术决策记录、经验总结。

唯一有价值的技术文档是 `docs/scraper-iteration-plan.md`（采集器调研）。

## 二、改善方案

### Phase 1: 基础设施搭建（立即执行）

#### 2.1 创建工作区结构

在项目根目录创建以下结构：

```
workspace/                          # 当前根目录
├── docs/                           # 已有 — 产品文档区
│   ├── analysis-report.md          # 深度分析报告（已有）
│   ├── refactor-plan.md            # 重构计划（已有）
│   ├── scraper-iteration-plan.md   # 采集器计划（已有）
│   ├── e2e-iteration-report.md     # E2E 测试报告（已有）
│   ├── improvement-plan.md         # 本改善方案（新增）
│   └── decisions/                  # 技术决策记录（新增）
├── assets/                         # 新增 — 视觉素材区
│   ├── design/                     # 设计稿、UI 参考图
│   ├── bug/                        # Bug 截图
│   └── reference/                  # 参考设计、竞品截图
├── notes/                          # 新增 — 知识沉淀区
│   └── 每次踩坑后记笔记到这里
├── src/                            # 已有 — 代码文件夹
├── scripts/                        # 已有 — 脚本文件夹
├── tests/                          # 已有 — 测试文件夹
├── AGENTS.md                       # 新增 — AI 入职说明书
├── PROJECT.md                      # 已有 — 项目文档
├── WORKLOG.md                      # 已有 — 工作日志
└── worklog.md                      # 已有 — 工作日志（小写）
```

#### 2.2 编写 AGENTS.md

内容包含：
- 项目一句话简介
- 技术栈速查表
- 运行命令速查
- 当前版本和阶段
- 已知问题清单
- Git 分支和提交规范
- 工作区使用说明

#### 2.3 创建技术决策记录目录

`docs/decisions/` 采用 ADR (Architecture Decision Record) 格式：

```
# ADR-NNN: 决策标题

## 状态: 已采纳
## 日期: YYYY-MM-DD
## 背景: 遇到了什么问题
## 决策: 选择了什么方案
## 后果: 这个决策带来了什么好处/代价
```

### Phase 2: Git 提交流程修复（立即执行）

#### 2.4 建立"提交闸门"

**规则**: 每次迭代完成代码后，**必须先完成 git 提交，才能接受下一个新需求**。这是硬约束，不做例外。

**执行流程**:
```
1. 代码完成 → 2. bun run lint + tsc --noEmit → 3. git add <具体文件>
→ 4. git commit -m "类型: 描述" → 5. 更新 worklog → 6. 接受下一个需求
```

**不再允许**:
- 只写 worklog 不提交代码
- 文档单独成为一次 commit（必须和对应代码一起提交）
- E2E 测试报告每轮单独 commit（累积更新，N 轮合并为 1 次）

#### 2.5 E2E 测试报告提交策略调整

| 之前 | 之后 |
|------|------|
| 每跑一轮就 commit 一次 | 每 N 轮（如 5 轮）合并为 1 次 commit |
| 只更新数字 | 包含问题分析、截图、趋势 |
| 9 轮 = 9 个 commit | N 轮 = 1 个 commit |

### Phase 3: 开发流程修复（持续执行）

#### 2.6 引入四步构建循环

每个新功能/改动必须走完以下流程：

```
1. 讨论 (docs/)
   用户提出需求 → AI 提问、给建议 → 明确"做什么"和"为什么"
   输出: docs/ 下的需求文档或更新现有文档

2. Demo (可跳过或快速验证)
   对于小改动可跳过，大功能先做最小可用版本
   让用户在浏览器里看到效果，确认方向

3. 计划 (docs/decisions/)
   拆解步骤、识别风险、记录技术决策
   输出: 开发计划 + ADR 记录

4. 开发 + 测试 + 学习 (src/ + notes/)
   按计划编码 → 测试通过 → git 提交
   遇到坑 → 搞懂原因 → 记笔记到 notes/
   输出: 代码 + 知识笔记
```

**不是每个需求都要走完 4 步**。小 bug 修复只需 4 步，大功能需要走完全部。

#### 2.7 知识沉淀规范

每次遇到以下情况，必须在 `notes/` 下记录：
- 解决了一个反复出现的 Bug → `notes/bug-xxx.md`
- 调研了技术方案并做出选择 → 更新 `docs/decisions/`
- 发现了 XHS 反爬的新特征 → `notes/xhs-anti-scrape.md`
- E2E 测试发现了真实问题（不仅是"通过了"） → `notes/e2e-xxx.md`

笔记格式不要求正式，但必须包含：
1. 问题描述
2. 原因分析
3. 解决方案
4. 防止再次发生的措施

### Phase 4: 历史债务清理（一次性）

#### 2.8 压缩 E2E 重复提交

将 `43d5d74` 到 `2d15f9f` 之间的 9 个 E2E 报告更新提交压缩为 1 个。

#### 2.9 清理无用文件

以下文件不应出现在 git 中或工作目录中：
- `e2e-test.js` / `e2e-test.sh` / `screenshot-script.js` — 一次性脚本，应归档或清理
- `mini-services/xhs-scraper/index.old.ts` — 旧代码备份，应清理
- `playwright-report/` — 测试输出，已在 .gitignore 中
- `test-results/` — 测试结果，应在 .gitignore 中
- `public/upload/` — 上传目录，不应纳入版本管理

## 四、改善后的理想状态

```
每次迭代完成后:
  ✅ 代码已提交 git（按功能模块分组，非按文档）
  ✅ worklog 已更新（代码和文档同一 commit）
  ✅ 遇到坑时 notes/ 有新笔记
  ✅ 重大技术决策记录在 docs/decisions/

新对话开始时:
  ✅ AI 读取 AGENTS.md 自动了解项目全貌
  ✅ 不需要用户重新交代背景

项目查看时:
  ✅ git log 清晰反映功能迭代历史
  ✅ docs/decisions/ 记录每个"为什么这么做"
  ✅ notes/ 记录每个"踩过的坑"
  ✅ assets/ 有完整的 bug 截图和参考设计
```
