## 二、模块深度评估

### 2.1 仪表盘 (dashboard-view.tsx) — 59KB / 约1200行

**实际价值: 高 | 代码质量: 中 | 模块耦合度: 极高**

**功能:** 全局概览、账号卡片、热门话题、AI策略推荐、活动流、快速操作

**做的好的:**
- 已将假数据替换为真实数据驱动的指标计算（trend、sparkline、activity）
- 多源数据聚合展示（accounts + posts + trending + strategy）

**问题:**
1. **数据加载过重型** — 单次加载触发 6+ 并发请求 (accounts, posts, trending, strategy, export-check, ...)，首屏等待时间长
2. **AI 策略推荐完全依赖 AI** — 无 AI 配置时 fallback 虽可用，但 4 条静态建议与实际数据无关
3. **热门话题模块已废** — 数据全是过时的春季内容（春日穿搭、减脂餐），且依赖 ZAI SDK 的 `web_search`，无配置时直接废掉
4. **导出对话框嵌入仪表盘** — 职责越界，导出应该是全局功能

**改进建议:**
- 仪表盘应做骨架加载 + 分阶段渲染，避免 6+ 请求串行等待
- 热门话题模块要么移除，要么改为可手动维护的「话题库」
- AI 策略推荐应增加「基于数据规则」的 fallback（如「最近7天笔记数<2 → 建议提升发布频率」）

---

### 2.2 账号分析 (account-view.tsx) — 57KB / 约1100行

**实际价值: 极高 | 代码质量: 中 | 模块耦合度: 高**

**功能:** 账号列表、账号详情、采集触发、手动数据编辑、Cookie 采集、数据分析面板

**做的好的:**
- 三种采集模式（搜索、Cookie、手动）覆盖了不同使用场景
- 智能字段合并逻辑（mergeField）避免覆盖真实数据
- 账号对比功能实用

**问题:**
1. **单个文件 57KB 过于臃肿** — 包含列表、详情、图表、Tab 切换等所有逻辑，违反单一职责
2. **采集过程缺乏进度反馈** — 用户点了采集后只能看到一个 loading spinner，不知道当前在执行哪个策略
3. **Cookie 过期无提示** — Cookie 失效后采集返回 0 笔记，用户不知道原因
4. **采集失败重试机制缺失** — 一旦失败需要用户手动重试

**改进建议:**
- 拆分为 AccountList、AccountDetail、AccountScrape 三个子组件
- 增加采集进度指示（Strategy 1/2/3 当前执行到哪一步）
- Cookie 失效时自动检测并提示重新输入
- 增加自动重试（3次指数退避）

---

### 2.3 数据洞察 (analytics-view.tsx) — 71KB / 约1400行

**实际价值: 高 | 代码质量: 中低 | 模块耦合度: 低**

**功能:** 互动漏斗、分类趋势、受众画像（年龄/性别/兴趣/活跃时段）、内容质量分布、热力图

**做的好的:**
- 漏斗已从假数据改为真实互动数据
- 分类趋势使用了真实的时间对比分析
- 增加了模拟数据的免责声明（估算/参考标签）

**问题:**
1. **受众数据完全模拟** — 年龄、性别、兴趣、热力图全部用 `Math.random()` + `Math.sin()` 生成，虽有免责声明但用户体验差
2. **71KB 单文件是最大的 View** — 包含大量图表渲染逻辑，维护成本高
3. **图表组件重复造轮子** — 漏斗图、雷达图、热力图都是手写 SVG，而非使用专业图表库
4. **无账号切换** — 数据分析绑定了 selectedAccountId，切换账号需要回到账号列表

**改进建议:**
- 受众分析模块应标注为「暂未开放」或移除，避免给用户错误预期
- 引入轻量图表库（如 Recharts）替代手写 SVG
- 增加账号维度切换，支持跨账号对比分析

---

### 2.4 内容库 (content-view.tsx) — 82KB / 约1600行

**实际价值: 极高 | 代码质量: 中 | 模块耦合度: 极高**

**功能:** 笔记列表/网格/日历视图、筛选排序、笔记详情、草稿管理、发布计划排程、手动添加笔记、批量操作、数据导出

**做的好的:**
- 多种视图模式（grid/list/calendar/schedule）
- 筛选功能完善（分类、关键词搜索、排序）
- 发布排程功能有创意但实现不完整

**问题:**
1. **82KB 是整个项目最大的文件** — 职责过多：笔记浏览、草稿管理、排程管理、导出、手动添加
2. **发布排程仅存在前端 localStorage** — 重启后数据丢失，且没有实际推送发布能力
3. **日历视图缺乏实际功能** — 只显示排程，没有拖拽、快捷操作
4. **批量操作仅限删除** — 缺少批量导出、批量修改分类等实用功能

**改进建议:**
- 拆分为 NoteList、DraftManager、ScheduleBoard 三个独立模块
- 排程数据应持久化到数据库（新建 ScheduledPost 模型）
- 如果无法实际发布到小红书，排程模块应改为「内容日历」提醒功能

---

### 2.5 人设管理 (persona-view.tsx) — 31KB / 约600行

**实际价值: 中 | 代码质量: 良好 | 模块耦合度: 中**

**功能:** 创建/编辑/删除账号人设，用于 AI 内容创作时注入 persona 上下文

**做的好的:**
- 人设数据模型设计合理（语气、风格、受众、主题、关键词）
- 与 AI 创作模块打通，生成内容时会注入 persona

**问题:**
1. **使用频率低** — 大部分用户不会花时间配置详细人设
2. **人设模板缺失** — 没有预设模板，用户需要从零填写
3. **人设效果不可见** — 配置后人设在 AI 创作中的影响不够明显

**改进建议:**
- 增加预设人设模板（美食博主、穿搭博主、旅行博主等）
- 在 AI 创作页面直接显示「当前使用的人设」及其影响范围
- 支持从已采集的笔记中自动推荐人设关键词

---

### 2.6 AI创作 (creator-view.tsx) — 61KB / 约1200行

**实际价值: 极高 | 代码质量: 良好 | 模块耦合度: 高**

**功能:** AI 内容生成、内容润色、写作模板、标签生成、草稿管理

**做的好的:**
- 写作模板（好物种草、美食探店、旅行攻略等）降低使用门槛
- 支持多种语气和风格选择
- 内容润色有四个明确目标（互动、清晰、情感、SEO）

**问题:**
1. **完全依赖 AI 配置** — 无 AI Key 时所有功能不可用，且错误提示不够友好
2. **生成结果无版本管理** — 同一主题多次生成会覆盖之前的结果
3. **内容质量无法评估** — 生成后没有质量评分或改进建议
4. **生成历史记录缺失** — 无法回顾之前生成过的内容

**改进建议:**
- 增加「离线模式」：使用模板生成结构化草稿（标题框架、内容大纲、标签建议），不依赖 AI
- 增加生成历史，支持对比不同版本的生成结果
- 生成后自动调用 AI 质量评分

---

### 2.7 设置 (settings-view.tsx) — 25KB / 约400行

**实际价值: 高 | 代码质量: 良好 | 模块耦合度: 低**

**功能:** 主题切换、通知设置、AI 大模型配置、数据管理、关于信息

**新模块评价:**
- AI 配置卡片设计合理，5 个内置提供商（含免费选项）
- 测试连接功能实用
- 配置保存到 JSON 文件，运行时生效

**问题:**
1. **localStorage + 文件双存储** — 前端存 localStorage，后端存 ai-config.json，可能不一致
2. **无配置导入/导出** — 换设备或清缓存后丢失
3. **数据管理卡片中「加载演示数据」和「清空数据」风险操作无二次确认** — 虽然有 confirm()，但体验差

- **内容库** → 依赖 DB + AI服务
- **AI创作** → 依赖 AI服务 + 人设 + DB
- **人设管理** → 仅依赖 DB

## 四、Critical 问题清单

### 4.1 架构层面

| # | 问题 | 严重度 | 影响范围 |
|---|------|--------|---------|
| 1 | 单页应用所有 View 同时挂载到 DOM，内存占用大 | HIGH | 全局 |
| 2 | 前端 View 直接 fetch API，无 React Query/SWR 数据缓存 | HIGH | 所有模块 |
| 3 | API Route 中大量重复的 JSON 序列化/反序列化 | MEDIUM | 所有 API |
| 4 | 无认证/授权机制 | MEDIUM | 全局 |
| 5 | SQLite 单文件数据库，无并发写入保护 | MEDIUM | 数据层 |
| 6 | `.next` Turbopack 缓存导致路由识别失败（已出现多次） | HIGH | 开发体验 |

### 4.2 功能层面

| # | 问题 | 严重度 | 影响范围 |
|---|------|--------|---------|
| 7 | ZAI SDK 仍然在 4 个文件中被直接导入（strategy, trending, xhs-scraper） | HIGH | AI/采集 |
| 8 | 受众分析（年龄/性别/兴趣/热力图）100% 假数据 | MEDIUM | 数据洞察 |
| 9 | 发布排程仅存 localStorage | MEDIUM | 内容库 |
| 10 | 热门话题模块数据过时且依赖废弃 SDK | HIGH | 仪表盘 |
| 11 | AI 评分字段 `aiScore` 在 schema 中是 Float 但 demo seed 写的是 0-10 范围 | LOW | 数据一致性 |
| 12 | `xhs-scraper.ts` 36KB 的遗留文件仍在使用 ZAI SDK | HIGH | 采集模块 |

### 4.3 代码质量

| # | 问题 | 严重度 |
|---|------|--------|
| 13 | View 文件平均 50-82KB，远超 800 行规范 | HIGH |
| 14 | 导出路由 GET/POST 两套逻辑重复（GET 有 CSV，POST 只有 JSON） | MEDIUM |
| 15 | persona API 重复的 safeJsonParse 调用可提取为 util | LOW |
| 16 | 17 个 API Route 中错误处理模式不一致（有些返回 500，有些返回 400） | LOW |
| 17 | TypeScript 存在 ~15 个编译警告（主要是类型不匹配） | MEDIUM |
| 18 | 无任何测试文件（单元测试、集成测试、E2E） | HIGH |

## 六、各模块价值评分

| 模块 | 用户价值 | 技术成熟度 | 维护成本 | 综合评级 |
|------|----------|-----------|---------|---------|
| 仪表盘 | 8/10 | 6/10 | 高 | B |
| 账号分析 | 9/10 | 7/10 | 高 | B+ |
| 数据洞察 | 6/10 | 5/10 | 中 | C+ |
| 内容库 | 9/10 | 6/10 | 极高 | B |
| 人设管理 | 6/10 | 8/10 | 低 | B- |
| AI创作 | 10/10 | 7/10 | 中 | A- |
| 设置 | 7/10 | 8/10 | 低 | B+ |

**核心结论:**
- **AI创作是最高价值模块**（10/10），但依赖外部 AI 服务是最大风险
- **内容库是最高维护成本模块**（82KB 单文件），拆分优先级最高
- **数据洞察是最低成熟度模块**（5/10），假数据区域过多影响专业度
- **仪表盘聚合度最高**但也是性能瓶颈，6+ 并发请求需优化
